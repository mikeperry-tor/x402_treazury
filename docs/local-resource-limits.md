# Local resource limits

Avoid creating additional limits. Arbitrary limits are largely considered
reliability hazards: they can reject valid actions or delay useful work for reasons
unrelated to the external service or blockchain. This inventory tracks existing
limits so operators can investigate unexpected failures. Listing a limit does not
justify retaining it or adding another one. Review the concrete resource or
correctness invariant before enforcing a limit; prefer removing redundant policy.

Funding reserve ranges and wallet payment caps are not resource limits and do not
authorize a second per-transfer ZEC budget. The operator's actual spendable ZEC
balance is the ZEC capital limit. Qualification adds reviewed allocation counts,
not a ZEC monetary budget. Ordinary funding has no recovery-count cutoff; safe
source closure and current authority govern replacements. Its `total_test_budget_usdc` bounds API authorizations
only; each potentially chargeable attempt is charged durably before disclosure.
Budget rejection emits WARN and a clear operation error; accepted work stays owned.

This guide covers foreground ownership, API caches, response transport and treasury
maintenance. The [network inventory](network-egress.md#remaining-timers-and-budgets)
tracks other timers, queues and polling policies.

`API_CACHE_TTL_SECONDS` in `src/limits.rs` supplies the shared catalog/price
default. A per-source catalog override controls that entry and its hints together.

Recognized insufficient-funds headers on a signed HTTP 402 allow the existing
next-wallet traversal immediately. The unused error body is dropped: its length,
truncation or inactivity cannot veto fallback. Every authorization remains
journaled, and the next wallet obtains and validates its own challenge.

Header-wait timers also include request upload, so a slow but progressing upload
can exhaust the read allowance. For gRPC, waiting for stream capacity is separately
bounded by that setting. See the [transport limitations](network-egress.md#timeout-budgets-and-concurrency)
for details. A timeout never proves that a signed action did not execute and never
grants automatic replay authority.

## Rejection and truncation

A runtime limit that rejects or truncates a logical operation after applicable
recovery must emit WARN or ERROR with safe resource and threshold/setting fields.
Individual HTTP/gRPC timeout attempts emit DEBUG while their owning workflow
determines retrying or terminal severity. Optional speculative document
origin probes report oversized candidates at DEBUG with the same safe fields and
visible `too_large` outcome; explicit document requests retain WARN. This is a
diagnostic distinction, with identical byte bounds and no partial success.
Normal capacity waits, retained
observation deferrals and disposable cache eviction belong at DEBUG; they do not
establish failure or permission to retry. Rejections must also provide explicit evidence for the affected consumer: a tool error or truncation
marker, HTTP error or CLI error. Identify the resource, limit and adjustment
setting where applicable. Do not log private content, credentials or sensitive
URLs to explain it. Tests verify consumer-visible evidence and logs.

Normal page boundaries, cache freshness expiry, keepalives, retry-delay waits,
observation cooldowns and successful scheduling cadences do not signify failed work.
They do not emit a capacity warning merely because a page is full or a due time has
not arrived. Optional cover episode completion and signed/qualification authority
expiry have their own contracts; fixture deadlines are test controls, not serving
resource limits. A capacity diagnostic never creates retry or financial authority.

Never present an incomplete document as complete. Completed tool outputs are returned in full; retired `max_response_chars` settings
reject visibly. Explicit provider `max_description_chars` controls only descriptions,
separately from download/memory and image bounds. An oversized paid response may already have settled
and grants no automatic retry. These visibility requirements do not justify adding
another bound.
